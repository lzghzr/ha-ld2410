# 杰理产品移植参考

移植时先按芯片、容器和布局分层，再按功能逐项重建映射。下面的分层来自已检查的备份样本，适合作为起点，不替代目标包审计。

| 产品或样本 | 起始判断 | 移植策略 |
| --- | --- | --- |
| LD2401C V2.53、LD2410 V2.44、LD2410B V2.44 | AC632N、双镜像几何和应用规模接近 | 可复用尾部代码设计、BLE/VM API 搜索方法和验证脚本；逐镜像重定位地址并做硬件验证 |
| LD2410B V2.04 | AC632N 的较早应用布局 | 单独建立 app 尾端、VM 边界、广播构造和命令分发表，不能沿用新版本绝对地址 |
| 2416、LD2410AA、LD2411/LD2411-S、LD2460、HLK-SW01S | AC632N 但功能和布局差异更大 | 先确认雷达状态、广播路径和 VM 几何，再决定能否复用某个 hook |
| LD2412、LD2450、LD2451 | AC635N 芯片族 | 使用对应工具链和 ABI 重新反汇编、链接、封装；AC632N 地址和调用约定只作概念参考 |
| ADT6101P、LD6002B `.bin.ufw` | 容器形态与标准 UFW/JLFS 不同 | 先识别外层格式、校验和、启动区及升级入口，再设计功能移植 |

## 可复用部分

- 从原厂唯一调用点接入，并保留原函数的参数、栈和返回约定。
- 在应用末尾建立专用代码区，使用目标包自己的链接脚本和执行上限。
- 复用目标固件已经存在的 BLE 广播 setter、VM 读写、随机填充和 CRC 例程。
- 让 A603/A604/A2 等新命令通过目标已有分发框架进入，并保留原厂错误码风格。
- 用同一套报告结构记录 preimage、分支目标、空间、镜像、CRC、Key 和实机结果。

## 必须重新确认

- 芯片、指令集、编译器 ABI、RAM/Flash 地址和 app 映射起点。
- 主广播与扫描响应的构造点、控制器更新条件和连接态刷新方式。
- VM/PRCT/BTIF/EXIF 边界、条目类型和 OTA 保留内容。
- 版本号、设备名、Manufacturer Data 与目标 App/HA 的解析条件。
- 两个镜像是否都需要改动，以及目标升级器对封装、Key 和 CRC 的要求。

每完成一个目标型号，先交付静态报告和可恢复的实验包，再进行 OTA；把通过的硬件观测写入该型号自己的映射表。
