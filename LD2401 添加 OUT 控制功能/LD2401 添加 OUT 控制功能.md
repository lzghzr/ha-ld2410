## 1. 需求

1. 能**手动把 OUT 拉到指定电平**(低或高),并**保持**——即使雷达正在检测到人、自动逻辑想拉高,也不许被改回去;
2. 能**解除保持**,回到"检测到人才输出"的自动行为;
3. **不改变固件尺寸、镜像布局、引导区与 Key**——后续还要在这个包上叠加 BTHome 等功能,必须能合包。

## 2. 平台与固件基线

- 主控:杰理 AC6323A4(Q32S 核)。app 是 freestanding 二进制,载入地址 `0x1E00120`,长度 172852 字节,即占据 `0x1E00120 .. 0x1E2A454`。
- 固件容器 `.ufw`:JLFS 目录 + 自反 LFSR 混淆 + `crc_hqx` 校验。**一个包内装两份 flash 镜像**(`type=0` 的 bank0 与 `type=32` 的 bank1),两份都带同一份 app.bin,所以打补丁要**两份都改**,不能只改一份。
- 为什么必须等长:bank0 有约 2.2KB 空档,增量能被吸收;bank1 只有 154 字节空档,app 一旦变大就要按 256 字节向上取整扩镜像,**同时把 bank1 的 VM 起点上移、设置存储区缩小**(旧参数可能丢失)。本方案零新增代码,两份镜像尺寸都不动,所以这个代价完全没有发生。

## 3. 协议要点

下行帧:`FD FC FB FA | 长度(2,LE) | 命令字(2,LE) | 命令值(N) | 04 03 02 01`。
应答帧:命令字 = 原命令字 `| 0x0100`,载荷前 2 字节是状态(`0000` 成功 / `0100` 失败),再跟各命令自己的返回值。

- `0x00FF` 进入配置(`b[0x4388]=1`),`0x00FE` 退出配置(清 `b[0x4388]`)。除 A8 外,所有命令在入口先做会话检查,未进配置就回 status=1。
- `0x00A6` 是**手册外命令**(手册 V1.00 未收录):原厂语义为"参数 1 = OUT 拉高 + 置保持标志;参数 0 = 清保持标志 + 拉低"。本功能就在这条命令上扩展。
- 配置期间原厂本来就会暂停雷达上报(`0x1E03116` 那处门控),本方案**没有动它**;退出配置后上报照常恢复。

## 4. 原厂实现的逆向结果(地址级)

### 4.1 命令分发与寄存器约定

命令处理器的序言(`0x1E00FA8`–`0x1E00FE2`)先把后续都要用的基址装好:

| 寄存器 | 值 | 含义 |
|---|---|---|
| `r10` | `0x4340` | RAM 状态结构 → 保持标志 = `b[r10+0x1d4]` = **`b[0x4514]`**、配置标志 = `b[r10+0x48]` = `b[0x4388]` |
| `r13` | `0x1E5000` | **外设(GPIO)基址** → OUT 引脚 = `[r13]` 的 bit0 |
| `r15` | `0x4740` | 命令结构:命令字 `h[r15+0x194]`、命令值 `h[r15+0x196]`;长度在 `r6` |
| `r11` | 0 | 常量 0 |
| `r12` | 1 | 常量 1 |

> 注意:`r10` 和 `r13` 是两个不同的基址(前者 RAM、后者外设)。把 `r10` 当成外设基址是很容易犯的错,会导致"以为 A6 不驱动引脚"的错误结论。

`0x1E0114C` 起是一串比较:`0x00`→`0x1E01606`、`0x0B`/`0x1B`、`0x24`→`0x1E01656`、`0x25`→`0x1E0166C`、`0xFE`→`0x1E0167E`,其余(非 0xFF)全部落到 `0x1E018FC`。A0–C0 走 `0x1E010EE` 的半字偏移表分发。

### 4.2 保持标志与自动输出逻辑

- 保持标志是 RAM 里的 **`b[0x4514]`**,代码里只当**布尔**用,不区分高低。
- 自动输出逻辑在 `0x1E030A2`–`0x1E0310E`,每个处理周期都会走到其中一个分支。分支里先读 `b[0x4514]`:**非 0 就整段跳过引脚驱动**;为 0 才按检测结果和辅助控制设定的极性(命令 `0xAD` 写入的结构,偏移 `+0x154/+0x155/+0x156` = mode / threshold / out_level)改写引脚。

⇒ "保持"的实现方式就是"把标志置 1,让自动逻辑闭嘴",不需要额外的互斥机制。

### 4.3 OUT 引脚的实际写者

`OUT` = GPIO `0x1E5000` bit0。把"哪些代码会写这个端口字"按寄存器数据流扫一遍,只有三类:命令路径、自动输出逻辑、以及引脚初始化辅助函数(配其它引脚方向/上下拉,不参与业务)。

命令路径里 **高、低两个方向共用同一句写回**:

```
0x1E01920:  [r2 + 0x0] = r0        ; r2 = r13 = 0x1E5000
```

- 高电平路径 `0x1E0191C` 先算 `r0 = r1 | 1`(置 bit0),直接落入 `0x1E01920`;
- 低电平路径在 `0x1E01302`–`0x1E0130C` 读端口、算 `r0 = r1 & 0xFFFFFFFE`(清 bit0),再 `goto 0x612` **跳进同一条 `0x1E01920`**。

**结论:A6(0) 是真正把引脚驱动到低电平,不是"冻结当前电平"。** 这一点已由实测确认:有人在雷达前触发高电平时发 A6(0),引脚依然被拉低并保持。

### 4.4 三个相关处理体

| 命令 | 处理体入口 | 原厂行为 |
|---|---|---|
| `0x00A6` | `0x1E012DA` | 会话检查 → 长度必须为 4 → 参数 1:置保持标志 + 引脚置高(`0x1E01906`) → 参数 0:清保持标志 + 引脚置低(`0x1E012F4` 与 `0x1E01302`) → 其它参数跳错误尾 `0x1E01752` |
| `0x0024` | `0x1E01656` | 回 `0x1E1B476` 处 7 个半字的固定结构(语义未证实,厂商 App 不使用) |
| `0x0025` | `0x1E0166C` | 空载荷,只回"配置会话是否有效"(status 0/1) |
| `0x00FE` | `0x1E0167E` | 清 `b[0x4388]`(配置标志)**和 `b[0x4514]`(保持标志)** |

- 0x24、0x25 的处理体各只有 **18 字节**,都终止于共享的 ACK 发送点 `0x1E018BC`。该共享点的调用约定是:`r0` = 载荷指针、`r1` = 载荷长度(半字)、`r2` = 命令字、`r3` = 状态。
- 全镜像 6.4 万条指令扫描确认:0x25 处理体的**唯一外部入口**就是那条分发比较(0x24 同理)。所以这段代码是"无外部引用的叶子",可以安全征用。

## 5. 改造设计:三条需求怎么落地

| 需求 | 原厂的障碍 | 改法 |
|---|---|---|
| 手动低/高要**保持** | 只有"参数 1"会置保持标志;"参数 0"是清标志,自动逻辑下一拍就改回去 | 把参数 0 的标志写入从"清"改成"置"(`r11`→`r12`),引脚照原样拉低 |
| 要能**解除** | 原厂没有这个状态 | 新增参数 **2**:跳进新处理体,清保持标志后回显 |
| 退出配置不能丢保持 | FE 原厂会清保持标志 | 把 FE 里那句"清保持标志"改成重复清配置标志(等长替换) |
| 新代码不能撑大固件 | 尾部追加必然使包变大、吃 VM 区 | 征用**原 0x25 处理体**那 18 字节,同时停用它的分发比较 |

### 6.1 逐处反汇编对照

**① 停用 0x25 分发(`0x1E01160`)**

```
原厂:  1e01160: 57 e2 84 02   if (r7 == 0x25) goto 0x508   ; -> 0x1E0166C
改后:  1e01160: 00 f2 84 12   if (r0 != r0)    goto 0x508   ; 恒假,永不跳转
```
0x25 落空后沿 `0x1E0116A` 的 `if (r7 != 0xff) goto 0x78c` 进入未匹配命令路径 `0x1E018FC`,即清解析状态后回主循环。

**② A6 参数路由(`0x1E012F0`)**

```
原厂:  1e012ec: if (r0 == 0x1) goto 0x616     ; 参数 1 -> 0x1E01906(置标志+拉高)
       1e012f0: if (r0 != 0x0) goto 0x45e     ; 其它参数 -> 错误尾
改后:  1e012ec: if (r0 == 0x1) goto 0x616     ; 未改
       1e012f0: if (r0 != 0x0) goto 0x378     ; 参数 2/3/... -> 0x1E0166C
```
入口处已有的会话检查(`0x1E012DA`)与长度检查(`0x1E012E8`,`r6` 必须为 4)都保留,所以新处理体只在"会话有效 + 长度正确"时才可能被执行。

**③ A6 参数 0 改为"置保持"(`0x1E012F4`)**

```
原厂:  1e012f4: 1b f9 d4 a1   b[r10 + 0x1d4] = r11   ; r11=0,清保持标志
改后:  1e012f4: 1c f9 d4 a1   b[r10 + 0x1d4] = r12   ; r12=1,置保持标志
```
其后原厂的引脚拉低序列**完全保留**(`0x1E01302`–`0x1E0130C`):读端口 → 清 bit0 → 跳 `0x1E01920` 写回。所以参数 0 = 置保持 + 拉低。

**④ 新处理体(`0x1E0166C`,18 字节,与 0x25 处理体等长)**

```
改后:  1e0166c: 20 e0 71 10   if (r0 != 0x2) goto 0xe2   ; -> 0x1E01752 原厂 A6 错误尾
       1e01670: 1b f9 d4 a1   b[r10 + 0x1d4] = r11       ; 清保持标志(r11=0)
       1e01674: e0 a1         r0 = sp + 30               ; 回显指针(A6 入口已存参数)
       1e01676: 11 70         r1 = 0x1                  ; 1 个半字的回显
       1e01678: 62 7a         r2 = 0xa6                 ; 命令字 A6
       1e0167a: 03 70         r3 = 0x0                  ; status=0
       1e0167c: 1f 19         goto 0x23e                ; -> 0x1E018BC 共享 ACK 发送
```
错误分支不是新代码:它跳进原厂 A6 自己的错误尾 `0x1E01752`(那里会设 `r2=0xA6`、`r3=1`,再走 `0x1E01836` → 共享 ACK),所以 `A6=3` 得到的是**原厂风格的错误应答**。

**⑤ FE 不再清保持(`0x1E0168C`)**

```
原厂:  1e01688: 16 f9 48 00   b[r0 + 0x48] = r6   ; r6=0,清配置标志
       1e0168c: 16 f9 d4 01   b[r0 + 0x1d4] = r6  ; 清保持标志  <-- 被改掉
改后:  1e0168c: 16 f9 48 00   b[r0 + 0x48] = r6   ; 变成再清一次配置标志
```
等价于"FE 只清配置标志,保持标志原样保留"。

## 7. 打补丁后的行为

| A6 参数 | 保持标志 `0x4514` | OUT 引脚 | 自动逻辑 |
|---|---|---|---|
| `0` | 置 1 | **清 bit0 → 拉低** | 被旁路,不会改回去 |
| `1` | 置 1 | **置 bit0 → 拉高** | 被旁路,不会改回去 |
| `2` | 清 0 | 不写 | 下一拍接管,按检测结果与 out_level 极性驱动 |
| `3` 及以上 | 不动 | 不动 | 不动(回错误应答) |

串口操作(256000,每步等应答):

```
进入配置   FD FC FB FA 04 00 FF 00 01 00 04 03 02 01
A6 = 0     FD FC FB FA 04 00 A6 00 00 00 04 03 02 01   拉低并保持
A6 = 1     FD FC FB FA 04 00 A6 00 01 00 04 03 02 01   拉高并保持
A6 = 2     FD FC FB FA 04 00 A6 00 02 00 04 03 02 01   解除保持
退出配置   FD FC FB FA 02 00 FE 00 04 03 02 01          保持状态不被清除
```

应答(实测抓帧):

```
FF    -> FD FC FB FA 08 00 FF 01 00 00 01 00 40 00 04 03 02 01
A6=0  -> FD FC FB FA 06 00 A6 01 00 00 00 00 04 03 02 01     status=0,回显 0
A6=1  -> FD FC FB FA 06 00 A6 01 00 00 01 00 04 03 02 01     status=0,回显 1
A6=2  -> FD FC FB FA 06 00 A6 01 00 00 02 00 04 03 02 01     status=0,回显 2
A6=3  -> FD FC FB FA 04 00 A6 01 01 00 04 03 02 01           status=1(参数非法)
FE    -> FD FC FB FA 04 00 FE 01 00 00 04 03 02 01  << 雷达上报帧随之恢复
```

限制:
- 保持标志在 RAM 里,**重启或掉电即回自动**(设计如此,不承诺掉电保持)。

## 8. 验证方法

**A. 静态**(脚本自动完成,见 §8 的 8 项)。

**B. 协议层**(串口,已实测):
FF/A6(0,1,2)/FE 各步都应回 status=0 并正确回显;A6=3 应回 status=1;退出配置后应立刻看到雷达上报帧(`F4 F3 F2 F1 ...`)。

**C. 物理电平**(万用表接 OUT 与 GND):
1. `FF → A6=0 → FE`,OUT 应为低并**保持**;此时人走到雷达前,OUT 不应被拉高;
2. `FF → A6=1 → FE`,OUT 应为高并保持;
3. `FF → A6=2 → FE`,OUT 应回到自动(无人为低、有人为高)。

**D. 回归**:
- 退出配置后实时上报正常(门控没被动);
- 普通调参命令(`0x61` 读参数、`0x60/0x64` 写参数)正常;
- BLE 重连后行为不变;
- 模块重启后回到自动。

## 9. 已知边界与未验证项

- **保持状态不跨重启**(RAM 标志)。
- **0x25 命令被停用**:分发被改成恒假后,它落到未匹配命令路径。该路径按静态分析不发送 ACK(与 `0xAF`、`0xB3–0xBF` 同路:清解析状态后回主循环),但**这一点没有上机验证**。风险很低:厂商 App(HLKRadarTool 1.6.112)反编译源码里所有 `FDFCFBFA` 帧共 74 个命令字,**没有 0x25,也没有 0x24**;手册 V1.00 同样未收录;HA 侧组件也不用它。
- **串口 `0xA0` 的版本号未改**(仍为 `0124500215041124`),因此不能靠版本号判断"刷没刷上",要用行为判据(§7 的帧、A6=3 的错误应答、或物理电平)。如需版本标识,可另改 app.bin `0x1E1B488` 起的后 4 字节。
- **本文针对 2.50.24110415**。其它固件版本(例如新模块出厂自带的 2.50.25082916,厂商未提供固件包)未做对照,补丁地址不保证适用。
---

### 一句话总结

在原厂 A6 命令上新增第三个状态(参数 2 = 解除保持),把参数 0 从"清保持"改成"置保持",把 FE 的"清保持"改成等长空操作,新逻辑塞进原 0x25 处理体那 18 字节;每份 app.bin 只改 23 字节,整包长度与布局不变,反向可逐字节还原原厂包。
